1-1. 記述言語

ツール記述言語ユーザワークフロー内部実行モデル (詳細は章2)
Terraform HCL (専用DSL) plan → apply DSLを解析してresource graph構築 → 全体の差分を一括計算 → 順次実行
CDK TS / Python / Java / C# / Go (汎用言語経由) synth → diff → deploy コード実行でCFNテンプレート生成 (synth) → CFN engineがapply
Pulumi TS / Python / Go / .NET / Java (各言語ネイティブSDK) preview → up コード実行中にengineへgRPCストリーミングで RegisterResource を逐次送信 → engineが随時差分判断・実行 (ランタイム経路に静的中間テンプレートなし)*
Carina Carina DSL (専用DSL、ファイル拡張子 .crn) plan → apply DSLを解析してresource graph構築 → 全体の差分を一括計算 → 順次実行

* Pulumiは ランタイム実行経路には静的中間テンプレートを持たない が、エコシステム全体には中間表現的なものがいくつか存在する: (a) pulumi convert でTF/CFN/BicepをPulumiコードに変換する際のPCL (Pulumi Configuration Language) は公式に「intermediate representation」と呼ばれる、(b) pulumi preview --save-plan で 静的planファイル (Update Plans) を生成して後で pulumi up --plan で適用可能 (Terraform plan -out 相当)。「中間IRが一切ない」とは言えない。

いくつかの注記:

  • 本ドキュメントの「CDK」はAWS CDKを指す: cdktf (Terraform JSONにsynth) やcdk8s (Kubernetes manifestにsynth) は別engineに対してsynthするCDK系の派生で、本ドキュメントでは扱わない
  • CDKはjsii: 実装はTypeScriptで、jsii (https://github.com/aws/jsii) がそれをPython/Java/C#/Goにbridgingする。ユーザは好きな言語を選べるが、APIのセマンティクスはTSが原本。
  • Pulumiは各言語ネイティブ: sdk/nodejs, sdk/python, sdk/go 等がそれぞれnative実装 (gRPCでengineと通信)。jsiiのような単一原本からの自動bridgingではない。多言語Component (MLC) は別建てのschema-driven codegenで実現 (詳細は §1-2)。
  • 「外部DSL」「内部DSL」「汎用言語ベタ書き」の三分類: 一般にDSLには2種類ある。外部DSLはホスト言語と独立した専用文法を持ち独自パーサが必要 (HCL, Carina DSL)。内部DSL (embedded DSL) はホスト言語の文法上で動き、関数・メソッドチェーン・型システムを駆使してDSL風のAPIを作る (CDK/PulumiのConstruct/Component APIはTypeScriptの内部DSLとも捉えられる)。CDK/Pulumiは厳密には「内部DSL + 汎用言語のベタ書き」のハイブリッドで、ユーザはAPIを呼ぶだけのコードも書けるし、ホスト言語の for/if/関数定義をフルに使ったコードも書ける
  • DSLと汎用言語のトレードオフ概観: 汎用言語を取ると言語そのものの抽象化機構 (関数 / クラス / ジェネリクス / 型システム) をそのまま流用できる。Pulumiの Output<T> のようにSDK側で「依存追跡や未知値伝播を表現する型」を提供することはあるが、これは ホスト言語の型システムの機能をSDKが活用しているだけで、ツール側が言語を拡張しているわけではない。静的型言語 (TypeScript / Java / C# / Go) で型を書けば誤った代入は静的に弾かれるが、Python / JavaScriptで型ヒントを書かなければruntimeまで分からない。一方外部DSLを取ると言語側の抽象化機構を自前で設計しなければならない代わりに、文法レベルで「望ましくない書き方」を禁止できる (ユーザの記述意思に依存しない)。抽象化機構の詳細は §1-2、それぞれの設計判断が「結果の予測性」とどうトレードオフするかは §1-3で扱う。

1-2. 抽象化機構

ツール単位 (複数リソースを束ねる抽象化)読み込み + インスタンス化の構文実体
Terraform module (子moduleは再利用、root moduleはデプロイ単位) module "network" { source = "./modules/network"; ... } (DSLレベルで読み込みとインスタンス化が一体) ディレクトリ (HCLファイル群)
CDK Stack (デプロイ単位) / ユーザ定義Construct (再利用単位) / L3 Construct (既製パターン)** ホスト言語の import で読み込み、new MyStack(app, 'main') / new NetworkComponent(scope, 'network', props) でインスタンス化 (DSLレベルでは読み込み構文を持たず、ホスト言語に委譲) TypeScriptクラス (jsiiで多言語化)
Pulumi Stack (デプロイ単位、設定単位) / ユーザ定義ComponentResource (再利用単位) / 既製Component (Crosswalk等) ホスト言語の import で読み込み、new NetworkComponent('network', args, opts) でインスタンス化 (CDKと同様にDSLレベルでは読み込み構文を持たない) 各言語ネイティブのクラス (TS/Python/Go)
Carina module (子moduleは再利用、root moduleはデプロイ単位) 読み込み: let network = use { source = './modules/network' }、インスタンス化: network { ... } (DSLレベルで分離) ディレクトリ (.crn ファイル群)

** CDKのL2 Construct (例: s3.Bucket、ec2.Vpc、rds.DatabaseCluster) は中間層で、サービスにより性格が大きく異なる: s3.Bucket のような単一リソース寄りのL2もあれば、ec2.Vpc (VPC + サブネット6個 + IGW + NAT Gatewayを暗黙生成) や rds.DatabaseCluster (Cluster + Instance + SubnetGroup + SG) のように複数リソース束ね寄りのL2もある。表では同列化を避けてL2を独立行に立てていない。

注: CDK/Pulumiでは個別リソース (L1 Construct、CustomResource) も同じ new 構文で扱うため、単位の階層が複数ある。本節の主眼は「複数リソースを束ねる層」だが、graph上のノードを構成する 個別リソース層 も同じ抽象化機構の軸上にあり、§1-3では両層を含めて自由度を比較する。両層の対応:

層TerraformCDKPulumiCarina
複数リソース束ね層 (本節の主眼) module "..." { ... } Stack / ユーザ定義Construct / L3 Stack / ユーザ定義ComponentResource / 既製Component use { source = "..." } + name { ... }
個別リソース層 resource "aws_s3_bucket" "foo" { ... } L1 (new CfnBucket(...))、L2 (new s3.Bucket(...) 等) は中間層 new aws.s3.Bucket(...) (CustomResource) aws.s3.Bucket { ... }

§1-2は「抽象化機構の分類」、§1-3は「その機構をユーザがどこまで動的に扱えるかの比較」 という役割分担。

Stack/root moduleはそれ自体も「複数リソースを束ねる抽象化」だが、同時に「apply/up/deploy の対象となるデプロイ単位」という別の役割も持つ (詳細は章5)。

各単位の構造

Terraform module

  • 公式: 「module.<MODULE NAME> is a value representing the results of a module block」 (公式ドキュメント expressions/references)
  • for_each なし → object、for_each 付き → map of objects、count 付き → list of objects
  • locals { my_mod = module.network } のような代入は可能
  • ただし source はリテラル文字列のみ (公式ドキュメント block/module)。OpenTofu 1.8+のearly evaluationでもstaticにしか解決できない (tfvars/env/リテラル変数のみ)
  • 言い換えるとmoduleは値だが、moduleのidentity (どのsourceをinstantiateするか) は静的にしか決められない

CDK Construct

  • Construct クラスはAWS非依存の汎用ツリー構造として aws/constructs リポジトリで実装されており、aws-cdk-lib (CDK) を含むCDK系 (cdktf / cdk8s等) で共有されている
  • 各Constructは親 (scope) と子 (children) を持ち、node.path (scope列を / で連結) で識別子が決まる (詳細は章5)
  • 主要な階層:
    • App (extends Construct): 複数Stackを束ねる最上位ノード。デプロイの起点
    • Stack (extends Construct): 1 CFNスタックに対応するデプロイ単位。Terraformのroot module相当 (apply/deployの対象)
    • L1 Construct (Cfn*): CloudFormationリソースの1:1ラッパ。Terraformの resource ブロック相当 (個別リソース層)
    • L2 Construct: ベストプラクティス込みの高レベル抽象だが、サービスにより性格が異なる 中間層。AWS公式の説明では 通常は単一CloudFormationリソースに対応 とされるが、ec2.Vpc (VPC + サブネット6個 + IGW + NAT Gatewayを暗黙生成)、rds.DatabaseCluster (Cluster + Instance + SubnetGroup + SG)、lambda.Function (Function + IAM Role + Log Group) のように複数リソースを束ねる例外も多い (s3.Bucket のような単一リソース寄りもある)
    • L3 Construct (既製パターン): 複数リソースを組み合わせたベンダ提供パターン (例: ApplicationLoadBalancedFargateService はECS Cluster / TaskDef / Service / ALB / Listener / TargetGroup / SG / LogGroup / IAM Roleなど10+リソースを束ねる)。Terraform Registryのmodule相当
    • ユーザ定義Construct: ユーザが再利用可能な抽象として自分で定義するクラス。Terraformの子module相当
  • 通常のTSクラスなので、関数引数/戻り値/コレクション格納/動的選択は構造的に可能

Pulumi ComponentResource

  • TS / Python / GoそれぞれのSDKでネイティブにクラスとして提供される
  • 主要な階層:
    • Stack (Pulumi): pulumi up する単位。CDKのStackのような「class」ではなく、設定とデプロイの単位 (1 stack = 1デプロイ環境)。Terraformのroot module相当
    • CustomResource: 個別リソース層、providerがCRUDを持つ。Terraformの resource ブロック相当
    • ユーザ定義ComponentResource: ユーザが再利用可能な抽象として自分で定義するクラス。「providerのCRUDを持たない論理リソース」で、複数の CustomResource や他のComponentを束ねるTerraformの子module相当
    • 既製Component: ベンダ提供の高レベルComponent (例: @pulumi/awsx のCrosswalk for AWS)。Terraform Registryのmodule相当
  • opts.parent: Componentの入れ子関係をURNに反映 (親typeが連結される、詳細は章5)。同名子リソースの別親下での共存や、親子の削除/作成順序の自動推論を可能にする
  • MLC (Multi-Language Components): TSで書いたComponentをPulumi schema化して各言語 (Python / Go / Java / .NET) のSDKを自動生成する仕組み。ベンダーが1言語で書いたComponentを全言語ユーザに提供できる (CDKのjsiiと類似のゴール、jsiiが言語橋渡しなのに対しMLCはschema-drivenなRPC)

Carina module (use 式で読み込み + 別構文でインスタンス化)

  • 単位はmodule = ディレクトリ (.crn ファイル群)。これはTerraform moduleと同じ位置づけ
  • 読み込みとインスタンス化がDSLレベルで分離されている:
    • let network = use { source = './modules/network' } でmoduleを 読み込み (内部では UseStatement メタデータとしてpath/aliasを登録、network という名前に束縛)。use 式自体はリソースを生成しない
    • let net = network { cidr_block = '10.0.0.0/16' } で インスタンス化 (binding名 network を呼び出して引数を渡す。これがリソース生成の起点)
    • 同一templateから 複数インスタンス化が可能: thing { name = 'alpha' }; thing { name = 'beta' } のように同じbindingを複数回呼べる
    • 読み込みとインスタンス化の分離自体はCDK / Pulumiも実現している (ホスト言語の import + new) が、それらはホスト言語の機能であってDSLの構文ではない。CarinaはDSLレベルの構文としてuse 式を持つ点が違い。Terraformは module {} ブロック1個に両者を一体化している
  • use 式は let 束縛RHSにしか書けない。関数引数 / list/map / if/for / exportsに書くと文法エラー。当初は文法上primary位置に含まれるが評価器が let RHSだけを処理する「構造と評価のドリフト」状態だったが、carina#2233 (2026-04-26 close) で grammarの方をtightenする方向で解決: use_expr の文法的位置自体が let 束縛RHSに制限された
  • source フィールドはリテラル文字列のみ: parserで Value::String 以外を弾く (carina-core/src/parser/mod.rs:1664-1669)。変数参照 (use { source = path }) や条件分岐 (use { source = if cond { './a' } else { './b' } }) はparse error。Terraformの source リテラル制約と同等。Carinaはこれに加えて use 式の位置自体も let RHSに制限する二段構えで動的選択を遮断している
  • インスタンス化の name { ... } 構文 (ModuleCall) は、同じbindingを複数のnamed binding (let a = thing { ... }) やanonymous (thing { ... }) で呼び分け可能

1-3. 結果予測性に効く記述自由度の所在

§1-2で各ツールの抽象化機構を見た。ここでは「ユーザがそれをどこまで動的に扱えるか」を比較する。§1-2で見た複数リソース束ね層に加え、graph形状に直結する個別リソース層も含めて比較する (例: for_each/count は個別リソース層にも束ね層にも適用される)。基準は 「実行前にコードを読んだ時点で、resource graphの形 (どんなリソースがいくつ、どう繋がって作られるか) と各ノードの属性値が具体的にどう決まるかを読み取れるか」 に直接効く範囲。

選定基準:

  • (i) resource graphの形 (ノード数とedge) または 各ノードの属性値 を変える自由度に直接効くこと
  • (ii) 表記/抽象化の層 で説明できること (実行モデル / 型 / state / identityは章2〜5で扱うので除外)

なお本章は言語選択の全評価ではなく、結果予測性に直接効く軸へ限定 している。学習コスト・テスト容易性・IDE統合・運用責任分界・ガバナンス容易性等の主観/状況依存の論点は本ドキュメントの範囲外 (詳細は §1-4末尾参照)。

この基準で選ばれた3つの自由度 (各自由度はgraph形状にも属性値にも適用される):

  1. 抽象化の追加ユーザが新しい抽象 (任意ヘルパー関数 / クラス / 薄いwrapper) を足せるか。graph形状側ではmodule / Construct / Componentの切り出し、属性値側では値計算ヘルパー (命名規則 / 環境別パラメタ計算 / 文字列処理) や型抽象が該当
  2. 複数量の制御同じ抽象や要素を何個展開するかを動的に決められるか。graph形状側では for_each/count でresourceノード数を動かす、属性値側では tags = { for k in keys: ... } のようなmap / list comprehensionで属性内コレクションの要素数を動かす
  3. 実装の切替どの実装を選ぶかを動的に決められるか。graph形状側では source ディレクトリやクラスの動的選択、属性値側では計算ロジックの動的選択 (ストラテジ的な分岐)

属性値の予測可能性は、運用上「このリソースは具体的にどう設定されているか」をコードから知りたい場面 (インシデント対応 / コンプライアンス監査 / セキュリティレビュー) でgraph形状と並ぶ重要性を持つ。生成AIがIaCコードを読解・修正する文脈でも、属性値計算の動的構造はAIの誤読・誤修正の主因になる (詳細はcross-DSL分析 carina-position.md §7)。先行版の本章は属性値を「4ツールとも差が出にくい」として対象外としたが、属性値計算の抽象化自由度にはTerraform (組込み関数のみ) < Bicep (func あり) < Carina (関数合成 + closure) < CDK / Pulumi (高階関数 + クラス継承) で明確な差があり、本版では予測可能性軸に統合する。

ただし「複数量の制御」だけはgraph形状と属性値の境界が曖昧で、同じ for 構文でも for_each でresource生成に流れればgraph形状側、tags map内に閉じれば属性値側、と用法で分かれる。両者はengineが「別ノード/別identityとして扱うか」で区別する (詳細は §1-3-3末尾)。

識別子・unknown値・依存解決・state操作のような 実行時挙動の所在 も別軸で、章5/3/4で深掘りする。

1-3-1. 「記述自由度の所在」の二層

ユーザの上記3つの自由度は、誰が制限するか で2つに分かれる:

区分仕組みユーザから見ると
言語が決める 文法・評価器・型検査でユーザの選択肢が制限される 書けない (文法エラー / 型エラー / 評価エラー)
規約に委ねる 文法上は何でも書けるが、lint・コードレビュー・社内ガイドラインで縛る 書けるが組織内で許されない

両者とも「ユーザの選択肢を狭める方向の制約」だが、強制力と組織コストが大きく異なる。

1-3-2. 4ツール × 3自由度の偏り

各セルはgraph形状側と属性値側の両方を含む評価:

対象TerraformCDKPulumiCarina

全体像:

  • Terraform / Carina = 言語が決める: graph形状の3自由度と属性値計算の3自由度すべてを文法で制限。抽象化の追加はTerraform = ユーザ定義関数不可で属性値計算ヘルパーも書けない、Carina = fn で属性値計算は書けるが高階関数なし、と度合いに差がある
  • Bicep (cross-DSL分析参照) = 言語が決める: Carinaと類似の中間 (func あり、高階関数なし)
  • CDK / Pulumi = 規約に委ねる: graph形状 (Construct/Component) も属性値計算 (関数 / 高階関数 / 外部lib) もホスト言語の機能をフルに使える、組織がlint・レビューで縛る

属性値計算の自由度差はTerraform < Bicep < Carina < CDK / Pulumiの順で表現力が上がる。これはgraph形状側では同列に「言語が決める」と評価される3ツール (Terraform / Bicep / Carina) でも、属性値側では明確な差 が出ることを示している。

これは記述言語選択 (外部DSL vs 汎用言語) と強い相関を持つ自然な帰結 (詳細は §1-3-4で議論)。

1-3-3. 二層のトレードオフ

言語が決める (Terraform / Carina)

得るもの

  • 「読めない書き方」を構造的に書けない → ベテランも新人も同じ表現力に揃う
  • 静的解析・LSP・自動修正ツールが効きやすい
  • レビュアーが「文法が通っているなら最低ラインは満たす」と判断できる
  • 組織コストが低い (規約を作って教育する手間が要らない)

失うもの

  • 逃げ道がない: 複雑な構成を表現したい時、文法の表現力を超えると別アプローチに逃げる必要がある
    • Terraform: dynamic ブロックはlimited、for_each の制約に苦しむ、結局module切ったり外部スクリプトで生成したり
    • Carina: fn と関数合成 (>>) で値計算の抽象化はできるが、高階関数や一級関数値がないため、関数を引数で渡したりmoduleを引数で受け取って加工する設計は書けない
  • 言語拡張のコストが高い: 新しい構文を追加するにはparser/evaluator/LSPすべて触る必要がある
  • 「言語の表現力」がツールの上限を決める: HCL / Carina DSLの表現力以上のことはできない

規約に委ねる (CDK / Pulumi)

得るもの

  • 逃げ道がある: 何でも書けるので、複雑な構成も表現可能。社内のベテランがutilを作れば全員が使える
  • 言語のエコシステム (npm, PyPI等) と統合される
  • IDE/デバッガ/テストフレームワークが普通に使える
  • ツール側の実装コストが低い (ホスト言語に乗っかる)

失うもの

  • 「読めない書き方」を防げない: ループ・条件・継承を駆使したコードがチームに混入する
  • 規約の維持コスト: lintルール、コードレビュー、オンボーディング教育、すべて組織が負担する
  • 「ベテランしか保守できないコード」が生まれやすい
  • 表現力の差がチーム内のスキル差として顕在化する

「複数量の制御」の境界: graph形状 vs 属性値

3自由度のうち「複数量の制御」だけは、同じ構文でも適用位置でgraph形状と属性値のどちらに効くかが分かれる。区別の基準は 「engineが別ノード/別identityとして扱うか」:

  • graph形状側に効く: for_each = var.subnet_cidrs のようにresourceブロックやmodule呼び出しで使われると、要素ごとに別resourceノード (別identity) が生成される。要素数の動的化はそのままノード数の動的化
  • 属性値側に閉じる: tags = { for k in keys: k => format(...) } や policy_statements = [for s in stmts: { ... }] のように属性内のコレクション生成で使われると、ノード数もidentityも変わらず属性値の中身だけが動く

両者は同じ for 構文を使うが、結果予測性への効き方が異なる。graph形状側の for_each はplanで「resourceがN個増減する」として現れ、属性値側の for は「あるresourceの属性Xが複雑な値になる」として現れる。AI修正やレビュー時の認知負荷も別物。

§1-3-2表の「複数量の制御」セルは両者を一括で評価しているが、評価対象を分解するときはこの境界を意識する必要がある。

1-3-4. 「記述自由度の所在」と「コードからの結果予測性」の因果

ここまで見た二層は、4ツールの「コードからの結果予測性」の差を説明する (記述自由度に起因する範囲で)。

ツールコードからの結果予測性 (記述自由度に起因する範囲)
Terraform高い (graph形状・属性値とも for_each / dynamic 使用時、およびmodule経由で低下)
CDK書き方依存 (graph形状・属性値ともL1ベタ書きなら高、ループ/条件/継承/高階関数を駆使すると低)
Pulumi書き方依存 (同様)
Carina高い (graph形状: for のdeferredはplan表示で確認可能。属性値: fn で値計算が抽象化されるが高階関数なしのため動的差し替えは不可。いずれもmodule経由で低下)

説明:

  • 言語が決める範囲が広いと、「予測しにくい書き方」が文法で書けないので、結果予測性は構造的に高い
  • 規約に委ねると、ベタ書きで予測性を保てるが、抽象化を使った瞬間に予測性が落ちる

つまり 「DSLだから読みやすい」のではなく、「『言語が決める』範囲が広いから (= 規約に委ねる範囲が狭いから) 読みやすい」。記述言語の選択と記述自由度の所在は 完全に独立とは言えないが、概念的に区別できる別軸: 実際は強い相関がある (外部DSLは言語が決める範囲を広く取りやすい / 汎用言語は規約に頼りやすい)。汎用言語でもSDKが Output<T> のような型を提供してunknown値伝播を表現するパターン (Pulumi、CDKのToken等、詳細は章3) はあるが、これは ホスト言語の型システムをSDK側で活用しているだけ で、(a) 静的型言語かつ (b) ユーザが型を書く慣習を採用したときにのみ効く。Pulumiが言語を拡張して制約を課しているわけではないので、これを「言語が決める」と評価するのは過大評価になる。汎用言語で言語レベルの制約を全面的に入れたIaCツールの実装例は本ドキュメントでは確認できていない。

なおこの予測性の議論はすべて 「抽象化を経由していない範囲」 に限定される。Terraform / Carinaのmodule、CDK Construct、Pulumi Componentのいずれかを呼び出した瞬間、呼び出し側からは中身が見えなくなる (リソース数・identity・依存関係、および本版で予測可能性軸に統合した各ノードの属性値)。抽象化境界の透明性は記述言語や記述自由度の所在ではなく「呼び出し側がどれだけ中身を読みに行く必要があるか」で決まる独立した軸で、各ツールのドキュメント文化・テスト文化・preview UIが補う部分。

抽象化境界の透明性は本ドキュメントで深追いしないが、次の3点で本章の議論と接続する:

  • 属性値統合の含意: §1-3で予測可能性軸をgraph形状 + 属性値に拡張したことで、module経由で隠される対象もgraph形状 (リソース数 / identity / 依存関係) だけでなく 各リソースの属性値 に広がった。「全S3 Bucketの暗号化設定をコードから機械的に確認」のような属性値レベルの監査は、抽象化境界を越えた先まで読みに行く必要がある
  • AI時代の含意 (cross-DSL分析 carina-position.md §7参照): AIの コンテキスト窓 と 局所読解性 は抽象化境界の透明性と深く関わる。AIがmodule中身までコンテキストに入れないと修正できない場合、透明性が低い抽象化はAI検証性・plan精度・静的監査の 前提条件を毀損する。透明性は予測可能性の内実ではなく、§7のAI時代議論を成立させる 射程条件
  • 他章との接続: 抽象化境界を越えた先のidentity安定性 / unknown値伝播は 章3 (型と未知値) と 章5 (identityと安定性) で扱う

上記予測性議論の射程を限定する重要な前提として記録しておく。

仮想的な組み合わせ

「ユーザの記述自由度をどこに委ねるか」(言語が決める / 規約に委ねる) と「記述言語の選択」(外部DSL / 汎用言語) の組み合わせ:

記述言語記述自由度の所在例性質
外部DSL言語が決めるTerraform / Carina読みやすい、表現力に上限
外部DSL規約に委ねる(動的source、任意関数を持つDSL)該当ツールなし
汎用言語言語が決める(該当するIaCツールなし)設計余地として開いている
汎用言語規約に委ねるCDK / Pulumi表現力高、規約維持コスト

「外部DSL × 規約に委ねる」が空席なのは 淘汰圧の結果: 専用文法を作っておきながら任意の動的選択を許すなら、汎用言語を使う方が経済的で、外部DSLを作る意味が薄い。

「汎用言語 × 言語が決める」もIaCツールでは事実上の空席。Pulumiの Output<T> やCDKの BucketProps のようにSDK側で型を提供してホスト言語の型システムを活用するパターンはあるが、これらは (a) 静的型言語かつ (b) ユーザが型を書いたときにのみ効く慣習で、ツール側が言語を拡張して制約を課しているわけではない。Pkl (Apple) のように汎用言語風だが評価モデルを制限するDSLは近いが、PklはIaCツールではなく構成データ出力DSL (詳細はcross-DSL分析参照)。この象限に 言語レベルで 全面的に寄ったIaCツールの実装例は本ドキュメント執筆時点で確認できておらず、設計の余地として残っている。

この組み合わせ分析が妥当かどうかは、より多くのツール (Pkl, Bicep, KCL, Cue等) との比較で検証する必要がある。本ドキュメントでは深追いしない。

1-3-5. Carinaの現在地

Carinaは「外部DSL × 言語が決める」位置取り。複数量の制御 (graph形状・属性値とも) と実装の切替は文法レベルで制限。抽象化の追加は中間的: ユーザ定義関数 fn (型注釈・再帰検出含む)・関数合成 >>・パイプ |>・部分適用 (closure) は実装済みで、属性値計算の抽象化 はTerraformより自由 (組込み関数依存ではなくユーザ関数で書ける) だが、高階関数 (関数を引数/戻り値に取る) と一級関数値は未実装 のため、属性値計算ロジックの動的差し替え (実装の切替 / 属性値側) は文法レベルで遮断されている。先行ドキュメント §5の「関数合成は現時点で重視していない」「宣言性を捨てない」は、合成自体は実装済みなので 「合成までは実装、高階関数化はしない方向」 と読み替えるのが正確。module一級値化 (issue #2233でgrammar tighten解決済み、use 式は let 束縛RHS限定) や高階関数の追加は将来選択肢として開いているが、本ドキュメントは現状比較が主題なので深追いしない。

1-3-6. 本節で扱わなかったこと (他章送り)

  • リソース識別子の所在: ユーザが書くか / ツールが自動生成するか。Terraform/Carina (named) はユーザ制御、CDK/Pulumi/Carina (anonymous) はツール側のランタイム自動加工。詳細は 章5 (identityと安定性) で扱う
  • unknown値の扱い: CDK Token / Pulumi Output<T> / Terraformの count/for_each エラー / Carinaのdeferred退避。詳細は 章3 (型と未知値) で扱う
  • 依存解決と実行順序: 4ツール共通でランタイム自動推論。詳細は 章2 (中間表現と実行モデル) で扱う
  • 構文と評価副作用のずれ: CDK/Pulumiの new は通常の言語慣習 (オブジェクト生成のみ、副作用なし) に見えるが、実際にはconstruct treeへの追加 (CDK) やengineへの RegisterResource RPC通知 (Pulumi) を伴う。Terraform/Carinaの宣言的構文 (resource ブロック / let foo = type { ... }) には対応する副作用がない。この論点は表記の見た目より評価時に何が起きるかが本体で、実行モデルの差として 章2 (中間表現と実行モデル) で扱う
  • state操作: ユーザが手動編集できるか / 規約で縛るか。詳細は 章4 (stateの所有) で扱う

  • 評価モデルによる制約: 純粋関数性 / 副作用の隔離 / 評価順保証 (Pklのlazy evaluation等) は本ドキュメントの範囲外

1-4. この章の小結

  • 記述言語 (§1-1): 外部DSL (Terraform/Carina) と汎用言語 (CDK/Pulumi、内部DSL + ベタ書きのハイブリッド) の選択は、抽象化機構と制御の所在の設計余地を規定する
  • 抽象化機構 (§1-2): 「複数リソースを束ねる抽象化」にはデプロイ単位 (Terraform/Carinaのroot module / CDKのStack / PulumiのStack) と再利用単位 (Terraform/Carinaの子module / CDKのユーザ定義ConstructとL3 / Pulumiのユーザ定義ComponentResourceと既製Component) の2種がある。L1/L2や CustomResource は個別リソース層でTerraformの resource 相当
    • Terraform module: ディレクトリ単位、module ブロックで参照。source はリテラル文字列のみ (実装選択は静的)
    • CDK Stack / ユーザ定義Construct / L3 Construct: TypeScriptクラス + new 式。jsiiで多言語化
    • Pulumi Stack (設定単位) / ユーザ定義ComponentResource / 既製Component: 各言語ネイティブのクラス + new 式。MLCで多言語提供
    • Carina module: ディレクトリ単位。読み込み (let name = use { source = ... }) とインスタンス化 (name { ... }) が分離。use 式は let 束縛RHSにしか書けない (issue #2233でgrammar tighten解決済み)。同一templateから複数インスタンス化が可能。moduleを一級値として扱う設計余地は将来選択肢として残る
  • 結果予測性に効く記述自由度の所在 (§1-3): resource graphの形と各ノードの属性値 を変える3つの自由度 (抽象化の追加 / 複数量の制御 / 実装の切替) を「言語が決める」か「規約に委ねる」かは、二層に分けられる。3自由度はgraph形状側と属性値側の両方に適用される
    • 「読みやすさ」は記述言語ではなく記述自由度の所在で決まる: 「DSLだから読みやすい」ではなく「言語が決める範囲が広いから読みやすい」。記述言語と記述自由度の所在は強い相関を持つが概念的に区別できる別軸
    • 「言語が決める」(Terraform/Carina) は読みやすさを構造的に保つ代わりに表現力に上限がある (逃げ道がない)
    • 「規約に委ねる」(CDK/Pulumi) は逃げ道がある代わりに組織の維持コストを生む
    • graph形状側で同列の3ツール (Terraform/Bicep/Carina) も属性値計算の自由度では差がある: Terraform (組込み関数のみ) < Bicep (func あり) < Carina (fn + 関数合成 + closure) < CDK/Pulumi (高階関数 + クラス継承 + 外部lib)
    • 「複数量の制御」はgraph形状側 (for_each でresourceノード生成) と属性値側 (tags map内 for) で効く先が違う。区別の基準はengineが別ノード/別identityとして扱うか
    • 抽象化境界の透明性は別軸で、記述言語/記述自由度の所在に依存しない
    • 識別子・unknown値・依存解決・state操作のような実行時挙動の所在は §1-3では扱わず、章5/3/2/4で深掘り

結果予測性に絞った理由

本章は「言語選択の全評価」ではなく、結果予測性に直接効く軸 に絞っている。言語選択で重要な軸は他にも多数ある: 学習コスト、既存人材との適合、エコシステム / ライブラリ流通、型安全、テスト容易性、リファクタリング耐性、レビュー容易性、IDE / LSP統合、CI/CD統合、デバッグ性、セキュアデフォルト、移植性、実行性能、運用責任分界、チーム規模適性、ガバナンス容易性、等。

これらを本ドキュメントで主軸にしない理由:

  • 章2-5に分散する論点 (型 / state / identity等) は各章で扱う
  • 組織論・運用論寄りの論点 (学習コスト、人材適合、ガバナンス等) は主観・状況依存で構造的比較が難しい

主題

「何を同一資源と見なすか」(identity) の規則と、コード構造を変えた時 (rename / move / refactor) にどこまで耐えるかの設計判断。stateの話 (章4) とは別の独立軸。

取り上げる論点

章1 §1-3-6から送られた論点

  • リソース識別子の所在: ユーザが書くか / ツールが自動生成するか
    • Terraform/Carina (named) はユーザ制御
    • CDK/Pulumi/Carina (anonymous) はツール側のランタイム自動加工

章1 §1-2で言及した論点 (詳細はここで)

  • CDK Construct node.path: scope列を / 区切りで連結する仕様
  • Pulumi opts.parent: URNのtype部に親typeが連結される
  • Stack/root module: デプロイ単位かつ「複数リソースを束ねる抽象化」、章5で深掘り

章1 §1-3-2表の「リソース識別子」行から送られた論点

  • Terraform: resource addressは <type>.<ラベル> で、ユーザが書いたラベルがそのまま使われる、ハッシュ化なし
  • CDK: CFN論理IDはconstruct path → MD5ハッシュで自動生成、overrideLogicalId() で明示制御可
  • Pulumi: URNはlogical name + parent type等をengineが組み立て、aliases で歴史的同一性を保てる
  • Carina: named bindingはbinding名そのまま (ハッシュなし)、anonymousはcontent-based hashで自動生成

章1 §1-3-2表後の段落で送られた論点

リソース識別子をユーザが日常的に意識する頻度:

  • Terraform/Carina: 別リソースから参照するためにコードに直接書く → 常時意識
  • CDK/Pulumi: ホスト言語の変数 (const bucket = new s3.Bucket(...) の bucket) 経由で参照、識別子は運用時 (cdk diff・コンソール・state操作・cross-stack reference・override・import) に表面化

物理リソース名との関係 (重要な区別)

論理ID/URN/binding名はstate/IR内部の識別子で、AWS上の物理リソース名 (S3 bucket名、IAM Role名等) とは別物。ただし関係はある:

  • リソース名を明示指定 (CDKの bucketName、Carinaの name 属性等) すれば、物理名は完全に制御できる。論理ID/URNとは独立
  • リソース名を省略 すると、CFNは <stack>-<logicalId>-<random> 形式 (例: mystack-mybucketf68f3ff0-abc123xyz) で自動生成。論理IDが物理名にサフィックスとして埋め込まれる

形式<stack>-<logicalId>-<random><logicalName>-<7hex> (terraform-bridgeベース)
例 (new ... ("mybucket"))mystack-mybucketf68f3ff0-abc123xyzmybucket-d7c2fa0
stack名を含むはいいいえ

→ Pulumiの方がCDKよりユーザフレンドリー。

物理名長の問題 (CDK特有):

  • AWSリソース名の長さ制限 (S3 63文字、IAM Role 64文字、Lambda Function 64文字、ALB Target Group 32文字 等) で切り詰められる
  • 例: MyAppProductionStack-MyServiceTargetGroupF68F3FF0 51文字がALB TGの32文字制限で MyAppProductionStaMyServ-XXXXXXXX のように真ん中削り
  • 元の意味のある部分が削られて識別がより困難になる

物理名問題の運用面の弊害:

  • 認知負荷 (一覧で何のbucketか分からない)
  • コミュニケーション摩擦 (ハッシュ付き名前を口頭/Issueで共有しにくい)
  • ドキュメント乖離 (設計時の名前と運用時の名前のズレ)
  • クロスサービス連携の不便 (IAMポリシーで正確な名前が必要)
  • URL/ドメインの見栄え (S3 website / CloudFront originでURLに直接出る)
