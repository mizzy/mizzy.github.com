plan(source, world) の world を速くする — 異分野の知見の適用可能性

2026-06-11 ・ 生成AI(Claude)との対話による探索 ・ 設計アイデアの整理。実装・実測はしていない。

派生元: Carinaの型システムと型理論（plan-as-compilation）。そこで整理した「IaCのコンパイルは二引数 plan(source, world) である」という見方を出発点にしている。

⚠️ 精度ノート

  • Carina側の事実(planが (source, world) の純関数であること、planがロックを取らずapplyがロック下で再計算するという契約、TOCTOUドリフト検出の存在)はcarinaのソース・ドキュメントで確認済み。
  • 異分野の研究・技術への言及(リース、OCC、DBSP / differential dataflow、Build systems à la carte、Salsa、self-adjusting computation、MESI、Dynamoの反エントロピー、CloudTrail / EventBridge / AWS Configの挙動と配信遅延)はAIの学習データ由来であり、一次ソースとの突き合わせはしていない。方向の参考として読み、設計に採用する前に各文献・各サービスの公式ドキュメントで確認すること。
  • 本ノートはアイデアの列挙であり、どの案も実測による裏づけを持たない。例外として、CloudTrailを変更フィードに使う案の二つの壁(リソースの一意な同定が難しい、ログが膨大)は、Terraformとの組み合わせで実際に試みた経験(筆者)に基づく確認済みの問題である。§2のConfig / Cloud Controlへの方針転換はこの経験を受けたもの。

1. 問題の構造

plan = コンパイルの分析で、IaCのコンパイルは二引数 plan(source, world) であると整理した。このうちworldの取得が遅い。信頼できるworldを作ろうとすると、全リソースをクラウドAPIへの同期GETで読む(refresh)ことになり、所要時間はリソース総数に比例し、レート制限にも当たる。

「信頼性 = 全リソースの同期GET」という等式をほどくと、攻め口は三つに分かれる。

以下、一見IaCと無関係な分野から、この三つに対応する知見を拾う。

2. ハードウェア / OS — dirty bitと無効化通知

CPUはメモリの全走査をしない。ページテーブルのdirty bitが「変わったページ」だけを教え、キャッシュ一貫性プロトコル(MESI系)は無効化通知を受けたキャッシュ行だけを再取得する。「全部読む」を「変わったと通知されたものだけ読む」に変える構造である。

クラウドにはdirty bitに相当する仕組みが既にある。CloudTrail / EventBridge / AWS Configは「どのリソースがいつ変更されたか」のイベントを配信する。これを購読すれば、worldは「planのたびに全GETで作るスナップショット」ではなく「変更イベントで維持される実体化ビュー」になり、refreshは「前回チェックポイント以降のイベント再生 + dirtyなリソースだけのGET」に縮む。API呼び出し数はリソース総数ではなく変更数に比例する(攻め口1と2)。

ただし「CloudTrailを購読する」という素朴な形には、Terraformとの組み合わせで実際に試みられて確認済みの壁が二つある。第一に同定の壁 — CloudTrailはAPI呼び出しのログであり、イベント中のリソースの表現(リクエストパラメータ、ARN、名前)がサービスごとに不揃いで、イベントをIaC側のリソース(state上のアドレス)へ一意に対応づけるのが難しい。第二に量の壁 — CloudTrailは読み取りを含む全API呼び出しを記録するため、ログが膨大になる。

CloudTrailを一次チャネルにする

API呼び出しのログ。リソースの表現がサービスごとに不揃いで、state上のアドレスへ一意に対応づけるのが難しい(同定の壁)。読み取りを含む全呼び出しを記録するのでログが膨大(量の壁)。

Terraformとの組み合わせで実際に確認済みの問題。

リソース指向の変更フィードにする

AWS Configのconfiguration item、またはEventBridgeで書き込み系・対象リソース型に絞ったルール。「リソース型 + リソースID」をキーに構成変更だけを配信するので、量の壁は構造的に小さく、同定の壁もリソースの語彙に最初から揃っている。

この経験はdirty bitの供給源の選定を変える。API呼び出しログ(CloudTrail)ではなく、リソース指向の変更フィード(AWS Configのconfiguration item、またはEventBridgeで書き込み系・対象リソース型に絞ったルール)を一次チャネルにすべきである。Configは「リソース型 + リソースID」をキーに構成変更だけを配信するので、量の壁は構造的に小さく、同定の壁もリソースの語彙に最初から揃っている。さらにCarina固有の追い風として、awsccプロバイダはCloud Control APIの上にあり、すべてのリソースが「リソース型(AWS::EC2::VPC)+ primary identifier」という一様な同定子を持つ。stateが保持する識別子とConfigイベントの語彙がほぼ一致するため、Terraform + CloudTrailで問題になった対応づけが、構造的に易しくなる可能性がある(未検証だが、検証する価値が高い)。それでも残る不一致(識別子の表記揺れ、複合識別子)に対しては、購読対象をstateに存在するリソース型・識別子の集合へ事前に絞り込み、対応づけられないイベントは「不明な変更 → 反エントロピー同期の対象」へ落とす、という保守的な設計で吸収する。

3. データベース — 増分ビュー維持と差分計算

§2の構図はデータベースの増分ビュー維持(incremental view maintenance)そのものである。さらに、DBSP / differential dataflowの系統は「入力の差分から出力の差分を直接計算する」一般理論を与える。これを当てるとplan自体を常駐クエリにできる。desiredとworldの差分(= plan)をworldの変更イベントが届くたびに増分更新し続け、carina plan は「計算する」コマンドから「維持されている差分を表示する」コマンドになる。

ここで言語側の性質が効く。増分化が安全なのは参照透明な計算だけであり、planが (source, world) の純関数であること — 静的段階の全域性と純粋性 — は、この最適化の前提条件をちょうど満たしている。汎用言語埋め込み型のツール(synthが外界を読みうる)では、この変換は同じ安全性では成立しない。

4. 分散システム — リース、楽観的並行性制御、反エントロピー

リース(Gray & Cheriton)は「期限付きの所有権があるあいだは、再確認なしで自分のキャッシュを信じてよい」という古典である。IaCでは「このstateの所有者だけがこのリソース群を書く」という運用前提がリースに当たり、前提が成り立つ間はrefresh自体が不要になる(攻め口3)。

楽観的並行性制御(OCC)は「古いスナップショットで作業を進め、コミット時に検証する」。Carinaは既にこの形をしている — planはロックを取らず、applyがロック下で差分を再計算する。これを意識的に推すと、plan時のworldの鮮度は正しさの問題ではなくUXの問題だと正当化できる。planは安いキャッシュで即答し、正しさの担保はapply側の検証に一本化する。リソース単位のversion比較(compare-and-swap的なapply)まで細粒度化する余地もある。

イベント配信は遅延も欠落もあるので、それだけに頼ると静かにずれる。Dynamo系の反エントロピー — 低頻度のバックグラウンド全同期で補正する — を併用する。Merkle木的なダイジェスト比較で「どの部分木がずれたか」だけを特定して同期する発想も借りられる。

5. コンパイラ / ビルドシステム — 依存追跡つき増分計算

Build systems à la carte、Salsa(rustcのクエリ基盤)、self-adjusting computation(Acar)の核は「入力が変わっていなければ再計算しない、変わっても依存の影響範囲だけ再計算する」依存追跡である。world側の変更イベントと組み合わせると、「VPCの1属性が変わった → それに依存する差分計算ノードだけ無効化 → planの大半はキャッシュヒット」という増分planが組める。§3の常駐クエリ案の、よりエンジニアリング寄りの実現形である。

6. 型システム — 所有権で「読まなくてよい」を証明する

この探索の文脈に最も合うのはこの角度である。Rustの所有権が「排他なら同期不要」をコンパイル時に証明するのと同じ形で、リソースごとに「書き手は誰か」を宣言のレベルで持たせる。自分(このstate)が排他所有するリソースはrefresh不要(自分の記録が真)とし、共有(コンソール操作や他パイプラインがありうる)と宣言されたリソースだけをイベント購読や同期GETの対象にする。

この宣言は単なる自己申告に留めなくてよい。IAM / SCPで「このロールしか書けない」が実際に強制されていれば、排他所有は運用上の仮定ではなく検証可能な前提になる。並行プログラム検証のrely-guarantee推論 — 環境の干渉をこの範囲と仮定して証明する枠組み — のIaC版である。型システム分析で見た「公称軸の部分型付け」と同様、宣言された前提を機構で裏づけるCarina好みの形に収まる。

7. 合成案 — 三層構造

Carinaに落とすなら三層になる。

  1. 既定排他所有が宣言・検証できるリソースはstateを真とし、APIを叩かない(リース / 所有権)。
  2. 共有リソースイベント駆動のdirty追跡(CloudTrail / EventBridge / Configを購読する常駐エージェントがworldビューを維持)+ 低頻度の反エントロピー全同期。planは常にビューから即答する。
  3. 正しさの錨apply直前のロック下でのリソース単位の再読・検証(OCCのコミット検証)。planの鮮度はここで最終担保されるため、1と2はすべて「速さとUXのための近似」と位置づけられる。

8. 限界

クラウドのイベント配信は遅延(分オーダー)と欠落があり、トランザクショナルでもない。したがって「plan時点の完全な鮮度」は原理的に買えない。買えるのは「有界の古さ + 変更量比例のコスト + applyでの最終検証」である。これはCarinaが既に持つ「planは予測であり、真実はapplyが確立する」という契約の延長線上にあり、契約を変えずに体感だけを変える種類の最適化だと言える。
