構成記述DSL 11個を同じ枠組みで見る

2026-04-26 · 初稿執筆中(2026-04-26着手)

IaC 4ツール(CDK / Pulumi / Terraform / Carina)の比較で使った「記述言語 × 記述自由度の所在」という2×2が、IaC以外の構成記述系DSLでも妥当かを検証した記録。Pkl / Bicep / KCL / CUE / Dhall / Jsonnet / Nickel / cdktf / cdk8s / Crossplane / Helmの11個を、同じ3自由度で点検する。

章1への反映は目的ではなく、各DSLを同じ枠組みで観察することそのものが成果物。

この記録の性質

これは生成AI (Claude / Codex)との対話形式による探索記録で、結論の確定ではなく、論点の整理と根拠確認を目的としている。複数回の訂正・スコープ調整を経たプロセスの記録であり、引用の前提としては弱い。

枠組みと結論 2軸・3自由度の定義、11DSLのサマリ表、2×2への再マッピング、4つの問いへの答え、出力の構造軸 Tier 1 — Pkl / Bicep / KCL / CUE 章1 §1-3-4で名指しした4つ。ハイブリッド象限が最初に見えた場所 Tier 2 — Dhall / Jsonnet / Nickel 構成記述DSLの代表例。同じハイブリッドパターンに独立に収束している Tier 3 — cdktf / cdk8s / Crossplane / Helm 派生・補助。1ツール=1象限という前提が崩れる例が出る Carinaの立ち位置 空席の象限、高階関数を入れた場合のシミュレーション、AI時代の予測可能性、現状機能点検

枠組み(再掲)

元にした2軸はこれ。

記述言語 外部DSL (専用文法・独自パーサ) / 汎用言語(内部DSL + ベタ書き)
記述自由度の所在 言語が決める(文法・評価器・型検査) / 規約に委ねる(lint・レビュー・社内ガイドライン)

3自由度

graphの形を変える自由度を3つに分け、それぞれを「言語が決める」か「規約に委ねる」かで判定する。表記/抽象化の層で説明できるもの。

  1. 抽象化の追加ユーザが新しい抽象(任意ヘルパー関数 / クラス / 薄いwrapper)を足せるか
  2. 複数量の制御同じ抽象を何個展開するかを動的に決められるか(ループ / for_each / count 等)
  3. 実装の切替どの実装(source / クラス)を選ぶかを動的に決められるか

なお章1 §1-3 (本版)は3自由度をgraph形状側と属性値側の両方に適用する形に拡張された。本cross-DSL分析の11DSL評価は主にgraph形状側に焦点を当てているが、属性値計算の自由度で見ると評価が変わるDSLもあり(特にPkl / KCL / Dhall / Jsonnet / Nickelのような構成データ出力DSL)、ここでは深追いしない(別issueで扱う余地がある)。

検証する問い

  1. 2×2マッピングは他DSLでも破綻しないか
  2. 「外部DSL × 規約に委ねる」象限(章1で空席)は本当に空か
  3. 「汎用言語 × 言語が決める」象限(章1で空席扱い)に該当するツールはあるか
  4. 3自由度は構成記述系DSL全般に通じる比較軸か、IaC固有の偏りがあるか

結論

4つの問いに対する答え。

問い1: 2×2マッピングは破綻しないか 部分的に破綻する
問い2:「外部DSL × 規約に委ねる」象限は本当に空か ほぼ空 — Nickelが部分的に近いが、実装切替は依然として言語が決める
問い3:「汎用言語 × 言語が決める」象限に該当するツールはあるか ない
問い4: 3自由度は構成記述系DSL全般に通じる比較軸か 部分的に通じるが、IaC固有の偏りもある

問い1: 2×2マッピングは破綻しないか

部分的に破綻する。理由:

  • 章1の単純2×2は「ツール = 1象限」を暗黙に前提していたが、多くのDSLは3自由度ごとに別の象限に落ちる
  • 特にPkl / KCL / Dhall / Jsonnet / Nickelは抽象化追加だけ「規約に委ねる」、複数量制御と実装切替は「言語が決める」という共通パターン(「外部DSL × ハイブリッド」象限)
  • CrossplaneはYAML層とfunction層で別象限を同時に占める (二層構造)
  • cdktfは複数量制御で2経路(ホスト言語 / Terraform) を併用できる

→ 章1 §1-3-4の2×2を3自由度の集計値ではなく3自由度ごとに別マップとして読み替えるのが正確。

問い2:「外部DSL × 規約に委ねる」象限は本当に空か

ほぼ空。Nickelが部分的に近い(3自由度のうち2つが規約寄り)が、実装切替(import path)は依然として言語が決める。

「外部DSLを作っておきながら3自由度すべてを規約に委ねる」DSLは本分析の11個には存在しない。章1の淘汰圧仮説(専用文法を作るなら何らかの制約を文法レベルで入れるはず、さもないと汎用言語で書く方が経済的)を補強する結果。

問い3:「汎用言語 × 言語が決める」象限に該当するツールはあるか

ない。Pulumiの Output<T> やCDKの BucketProps のようにSDK側で型を提供してホスト言語の型システムを活用するパターンはあるが、これらは(a)静的型言語かつ(b)ユーザが型を書く慣習を採用したときにのみ効くもので、ツール側が言語を拡張して制約を課しているわけではない。よって「言語が決める」と評価するのは過大評価になる。

これは理論的設計余地として開いているが、汎用言語のホスト機構と整合させるコストが高いと推測される。実装するとすれば「汎用言語の中にDSLを入れる」(F# のcomputation expression、Scalaのimplicit + macro等)アプローチが該当しうるが、IaC領域での全面実装例は確認できず。

問い4: 3自由度は構成記述系DSL全般に通じる比較軸か

部分的に通じるが、IaC固有の偏りもある。

  • 「実装の切替」(import pathの動的性) は11DSLすべてに当てはまる軸として機能
  • 「複数量の制御」も適用可能だが、IaC以外のDSL (Pkl / Cue / Dhall)では「graphの個数」ではなく「最終valueの集合サイズ」として読み替える必要
  • 「抽象化の追加」は普遍的だが、graph形状への影響はIaC以外では希薄(Pkl / Cueはgraphを出力しない、JSON/YAMLを出力する)

つまり3自由度は構成記述DSL全般の比較軸として有用だが、章1が前提としていた「graph形状を変えるか」という基準はIaC固有。

章1 §1-3-4の枠組みの強度評価

補強される部分 「外部DSL × 規約に委ねる」が空席である淘汰圧仮説、「汎用言語 × 言語が決める」もIaCでは事実上空席である現状認識(Output<T> 等はSDKが活用するホスト言語型システムの慣習であってツール側の言語制約ではない、と評価を改めた)
修正が要る部分 「ツール = 1象限」前提は粗い。3自由度ごとに別象限に落ちる「ハイブリッド型」DSL (Pkl / KCL / Dhall / Jsonnet / Nickel)を独立カテゴリとして認識する必要
追加が要る部分 「拡張ポイントを言語境界で開ける」設計(Crossplaneのfunction、PulumiのMLC)は章1の2×2では捉えきれない第三の選択肢

出力の構造軸

本分析を通して、章1 §1-3-4が暗黙に前提としていた区別が浮上した。DSLが何を出力するかで11DSLを分けると:

出力形態内容例
構成データ出力値ツリー(JSON/YAML/設定値)Pkl, KCL, CUE, Dhall, Jsonnet, Nickel
graph出力ノード + edgeの宣言Terraform, CDK, Pulumi, Carina, Bicep, cdktf, cdk8s, Crossplane, Helm

graph出力DSLのコードが出すのは:

  • (a)ノード集合:リソース宣言(type + 属性値)
  • (b) edge:リソース間の依存関係(参照、depends_on、opts.parent)

これは章1の3自由度(抽象化追加 / 複数量制御 / 実装切替)では捉えきれない別軸で、「DSLが何を出力するか」のレイヤの違い。

なお「graph出力」という括りは中間表現の経路を粗く扱っている。最終的にresource graphになるのは共通だが、コードからgraphに至る経路はツールごとに異なる:

直接出力Terraform, Carina, Bicep, Helm — DSL block / templateがそのままノード宣言
ツリー → synthでgraph変換CDK, cdktf, cdk8s — Constructツリーを組み立てて、synthでCFN/Terraform JSON/k8s YAMLに変換
RPCストリームPulumi — RegisterResource をengineに逐次通知、中間表現なしでengineがgraphを構築
YAML pipelineCrossplane — Compositionのpipeline内でfunction chainがgraphを組み立てる

経路は違うが、applyされる段階ではどのツールもresource graphを扱う。本分析の主題(3自由度)にはこの経路差は直接効かないので深追いしない。経路差自体は章1 §1-3-6「構文と評価副作用のずれ」として他章送りされており、章2実行モデルで扱う予定。

なおgraphを出力した後のstate管理 / 差分計算 / CRUD実行はDSLのレイヤではなくツール(engine / CLI)のレイヤの話で、本分析(DSLの比較が主題)では扱わない。

graph出力DSL × ハイブリッド象限という空席

「graph出力DSL」と「ハイブリッド象限(抽象化追加だけ規約寄り)」を組み合わせると、本分析の11DSLの中に空席がある。

Carinaの進化方向との整合

Carinaは現状「外部DSL × 言語が決める」象限(3自由度すべて言語で縛る)に位置するが、抽象化追加の自由度についてはハイブリッド象限の手前にいる。

機能Carinaの現状
関数定義(fn、型注釈・再帰検出)✅ 実装済み
関数合成(>>) / パイプ(|>) / 部分適用(closure)✅ 実装済み
高階関数(関数を引数/戻り値に取る、関数値が一級)❌ 未実装

もし将来Carinaが高階関数を導入すれば、3自由度の対応は次のように変わる:

  • 抽象化の追加:言語が決める → 規約に委ねる
  • 複数量の制御:言語が決める(for 式)のまま
  • 実装の切替:言語が決める(source リテラル + use の位置制限)のまま

これはPkl / KCL / Dhall / Jsonnet / Nickelと同じ「外部DSL × ハイブリッド(抽象化追加だけ規約寄り)」象限への合流を意味する。5DSLが独立にこの象限に収束した観察は、Carinaの進化方向とも整合する実用上の自然な落とし所と読める。

ただし設計上の注意点:高階関数を入れる際、関数値が「実装の切替」位置に染み出さないようにする境界設計が要る。例えば次のようなパターンが許されると、use 式のリテラル制約が骨抜きになる:

fn pick_module(env: string) -> Module { ... }     # 関数が module を返す
let net = (pick_module("prod")) { cidr = "..." }  # 関数呼び出し結果を module call の起点に

Carinaの現行設計(章1 §1-3-2)では use 式は let 束縛RHSにしか書けず、source はリテラル文字列のみ。高階関数を導入する際にこの不変条件を壊さないためには、Module 型を関数の戻り値型に置けないようにする等の型レベル制約が候補になる。

5DSLのうちPkl / KCL / Dhall / Nickelは構成データ計算(JSON/YAML出力) が主でgraph形状の予測性が論点にならないが、Carinaはgraphを出すDSLなので、ハイブリッド象限へ移行する際にこの境界線をどこに引くかが具体的な設計課題になる。

残された論点(cross-DSL分析)

  • Pklの構成データ計算vs IaCのresource graph:軸の読み替え(graph形状 → 最終value形状)が章1の前提を緩めることになるが、本分析は深追いしない
  • Crossplaneの二層構造の評価: function言語選択は「設計判断」というより「ユーザの実装選択」で、章1の枠組みとレイヤが違う
  • lazy評価の影響: Jsonnet / Nickel / Dhallのlazy性が「複数量の制御」「実装の切替」のセマンティクスに与える影響は未検証
  • Pulumi MLCとの比較:章1で言及されたMLC (Pulumi)は本分析では扱わなかった(CDKのjsiiと同じ「単一原本からの自動bridging」軸)

範囲外

  • 各DSLの詳細仕様の網羅(識別子・state・実行モデル等は本分析の対象外)
  • 個別DSLの優劣評価
  • 学習コスト・エコシステム等の運用論寄りの軸
  • 章1 §1-3-4への反映(本分析は独立完結させる)

以降の11個は同じテンプレートで書いてある: 1.記述言語の位置づけ / 2.抽象化機構 / 3. 3自由度の評価 / 4. 2×2配置 / 5.設計判断の議論。同じ順番で読めば、DSL間の差が構造として見えるようにしてある。

Tier 1 — 章1 §1-3-4で名指しした4つ

Pkl (Apple)TIER 1

公式: pkl-lang.org/main/current/language-reference/index.html
調査日: 2026-04-26

1.記述言語の位置づけ

外部DSL。Appleが公開した構成記述専用言語で、独自パーサと評価器を持つ。汎用言語の埋め込みではない。

評価モデルの特徴:

  • 純粋 (副作用なし)。例外は read() による外部リソース読み込み(公式: "Resources"章)
  • late-bound (object propertiesは遅延評価)
  • 文法はJava/Scala系の見た目。module, class, function, let 等の予約語

2.抽象化機構

単位構文役割
moduleファイル単位(.pkl)設定単位 / 再利用単位
classclass Foo extends Bar { ... }単一継承の型定義
functionfunction greet(b: Bird): String = "Hello, \(b.name)!"値の計算抽象
objectnew { ... } / amends { ... }レコード値、プロトタイプ的な拡張可

moduleの組み立て構文:

  • import "uri" で別moduleを値として読み込む(識別子に束縛される)
  • amends "uri" で別moduleをベースにし、上書き拡張する
  • extends "uri" で別moduleをクラス的に継承する

An import clause consists of the keyword import followed by the module URI of the module to import.

3. 3自由度の評価

3-1.抽象化の追加(ユーザヘルパー) — 規約に委ねる範囲が広い (ただし純粋関数限定):

  • ユーザ定義関数 function あり(型注釈・型制約付き引数)
  • 高階関数あり: Listing<Bird>(isDistinctBy((it) -> it.name)) のようにラムダを引数に渡せる(公式referenceより)
  • ユーザクラス class あり、単一継承で組み合わせ可能
  • 副作用がないので、関数を増やしても観測可能なグラフ形状の変化は限定的

ただし「グラフ形状を変える抽象」自体がPklのスコープ外。Pklは構成データ(オブジェクトツリー)を出力するのがゴールで、IaCツールが扱う「ノードとedgeを持つresource graph」とはレイヤが違う。3自由度を機械的に当てはめると次のように見える。

3-2.複数量の制御(graphの個数を動かす) — 規約 + 言語の合わせ技:

  • ループ構文(for, while)は言語にない
  • 代わりに標準ライブラリの map / filter / forEach 系メソッドで集合操作
  • if 式はあり、必ず else 必須(公式: "Every if expression must have an else branch")
  • 量を動的に決めること自体は普通に可能(List(1, 2, 3).map((i) -> new Server { port = 8000 + i }) のように)

つまり「量を動かすこと」は標準ライブラリで出来る、その範囲を「言語が決める」か「規約に委ねる」かは曖昧で、標準ライブラリAPIという中間層に押し込まれている。Terraformの for_each のような専用構文はないが、CDK/Pulumiのように for ループを直接書くこともない。

3-3.実装の切替 — 言語が決める(静的のみ):

  • import "uri" / amends "uri" / extends "uri" のURIは全てリテラル文字列のみ。変数や式で実行時に切り替えられない
  • 公式の文言: "the keyword import followed by the module URI of the module to import" (式ではなくURIそのもの)
  • これはTerraformの source リテラル制約、Carinaの use { source = ... } リテラル制約と同質

つまり「どのmoduleを使うか」はparse/load時に決まり、実行時に式で選べない。

4. 2×2配置

抽象化の追加規約に委ねる (関数 / 高階関数 / クラス継承が自由)
複数量の制御言語が決める + 標準ライブラリAPI (専用構文なし、ループ構文なし、map/filter 経由)
実装の切替言語が決める (URIリテラルのみ)

マッピング: 外部DSL × 言語が決めるに位置するが、抽象化の追加だけは「規約に委ねる」寄り。

これは章1 §1-3-4の「汎用言語(内部DSLの型を活用) × 言語が決める象限の部分実装」の裏返しの姿とも見える: Pklは外部DSLを選んだ上で「抽象化の追加」だけは汎用言語並みの自由度を許している。

5.設計判断の議論

Pklの位置取りは「外部DSLを選びつつ、構成データ計算の表現力(関数 / 高階関数 / 標準ライブラリ)は汎用言語に近づける」というハイブリッド。

外部DSL。data validation / configuration / code generationの特化言語。Goから派生したが言語仕様は独立。

評価モデル:

3-2.複数量の制御(graphの個数を動かす) — 言語が決める (comprehension限定):

  • 仕様: "Comprehensions define a clause sequence that consists of a sequence of for, if, and let clauses, nesting from left to right."

  • 使用箇所: listとstructの値構築に限定。トップレベルの for 文や手続き的ループはない
  • リソース束ね(Kubernetes manifest配列の生成等)はcomprehensionで表現

Pkl / KCLのハイブリッド性(抽象化追加だけ規約寄り)と異なり、CUEは3自由度すべてを言語で制限する純粋な「外部DSL × 言語が決める」象限。Terraform / Carina / Bicepと同じ象限の中でも、抽象化機構がunificationという独自の数学的基礎に乗っている点で特殊。

CUEの位置取りは「unificationに賭けた純粋関数型DSL」:

  • 順序非依存 / 結合則 / 交換則 / 冪等:これにより部分評価・統合・検証が可能(例: complete configuration = sum of partial configurations)
  • Turing不完全(有限性保証):仕様レベルで停止性を保つために、関数定義や再帰を許さない設計判断

得たもの

構成データの数学的取り扱い(constraintの自動検証、mergeの再現性、closed/open structでの型安全性)、Turing不完全による停止性保証、validation/policyとしての強さ。

失ったもの

命令的な計算ロジックの抽象化(ヘルパー関数で名前生成 / 環境別ポート計算 / 文字列処理を書き直すのが難しい)、命令型プログラマの直感とのズレ。

実装の切替言語が決める (import静的)

マッピング: 外部DSL × ハイブリッド (Pkl / KCLと類似象限)。

Pkl / KCL / Dhallは3つとも:

  • 抽象化追加 = 規約に委ねる (高階関数あり)
  • 複数量制御 = 言語が決める (専用構文or組込み関数)
  • 実装切替 = 言語が決める (import静的)

という同一ハイブリッドパターン。これは「外部DSL × 関数値が一級な言語」の典型形である可能性が高い。

5.設計判断の議論

Dhallの位置取りは「Turing不完全 + 純粋関数型 + 静的import + 暗号学的hash」:

  • 再帰禁止 / Turing不完全:停止性保証、normal formへのreduce可能性、安全性
  • importのhash integrity: let pkg = https://example.com/pkg.dhall sha256:abc... でURL経由のimportにhashを付けて改竄検出可
  • normal form:どんなに抽象化を重ねても、最終的に評価するとnormal form (関数もimportも解決した形)に到達する

得たもの

停止性、再現性(hash付きimportで同じ結果を保証)、構成データの数学的厳格さ。

失ったもの

任意再帰の表現力、ストリーミング処理、部分的なlazy評価。

DhallはCUEと並ぶ「外部DSL × 言語が決める範囲が広い」象限の純粋実装だが、CUEがunification中心なのに対しDhallはlambda calculus + import というHaskell的な系譜。

3自由度のうち「抽象化追加」だけはPkl / KCLと同じく規約寄りに開放されているのは、設定値の計算ロジック(環境別パラメタ計算 / 型変換 / 命名規則)を再利用するために関数抽象化が実用上必要だから。CUEのように関数を捨てると、定型的な計算の再利用がどうしても辛くなる。

cdktfの位置取りは「CDKと同じ汎用言語ベース、synth先だけTerraform」:

  • CDKと完全に同じ象限に落ちる(汎用言語 × 規約に委ねる)
  • 違いはsynth先(CFN vs Terraform JSON)とproviderのカバレッジ(AWS専用vs Terraform Registry全部)
  • ホスト言語の for/if とTerraformの for_each/count を両方使えることで、ユーザは2経路を選択できる

4. 2×2配置

抽象化の追加YAML層 = 言語が決める (関数なし) / function層 = 規約に委ねる (任意言語)
複数量の制御function経由 (使う言語次第)
実装の切替XRのlabelによる動的選択(Composition Selector) + functionは静的

マッピング: 外部DSL (YAML) × 多層で、章1 §1-3-4の単純2×2に収まらない。

最も近いのは「外部DSL × 言語が決める (YAML層) + 任意言語 × 規約に委ねる (function層)」のハイブリッド。

5.設計判断の議論

Crossplane Compositionsの位置取りは「Kubernetes API上に構築された二層IaC」:

  • YAML層は宣言的に閉じている: KubernetesリソースとしてCRUD可能、kubectlで操作、kustomizeやHelmと組み合わせ可能
  • function層に拡張性を全部押し付ける:パッチ変換・命名規則・複雑なロジックはfunction側で書く。functionはOCIイメージとして配布、複数言語で書ける
  • Composition Selector: XRのlabelに応じて適用Compositionを動的に選択 → 環境別(dev/staging/prod)で別Compositionを使い分け可能、これはTerraform / Bicep / Carinaにはない動的選択軸

得たもの

Kubernetes API上の宣言性(kubectl get composition)、functionによる任意言語拡張、Composition Selectorによる環境切替。

失ったもの

全体像の見通し(YAML + functionコード + XRDの三者を読む必要)、デバッグ複雑化(function chainのどこで何が起きたか)、type safetyの弱さ(YAMLレイヤの型は動的)。

章1 §1-3-4の枠組みからの逸脱: Crossplaneは「外部DSL × 言語が決める」象限と「汎用言語 × 規約に委ねる」象限の両方に同時に足を置く設計。これは章1が想定していた「1ツール = 1象限」という単純化が成り立たない例。「functionを組み込めば任意のDSL/汎用言語の特性を取り込める」という拡張ポイントは、Bicepの func やCarinaの fn (両方とも内蔵)と異なり、ツールチェーン全体で多言語を許容するという設計判断。

これはIaCツール設計のトレードオフとして章1で触れられていない論点(本ドキュメント全体の射程外、章1 §1-4末尾参照)を浮上させる: 「拡張ポイントを言語境界で開ける」という第三の選択肢。PulumiのMLC (multi-language components)も類似の発想。

3-1.抽象化の追加 — 言語が決める寄り (Go templateの制限):

  • 関数値は一級ではない: Go templateの関数は事前登録されたものを呼ぶだけ、ユーザが関数を「変数に入れる」「引数で渡す」はできない

  • 専用構文として閉じている

  • ただしvalues.yamlでsubchartの有効/無効を切り替えたり、subchart間で値を渡したりは可能(condition, tags)

つまり「どのchartを使うか」は静的、「使うかどうか」は動的。Bicepのmoduleの if 条件と同質。

5.設計判断の議論

Helmの位置取りは「Go template + YAML mix-in」:

  • templateベース: YAMLをそのまま書きつつ、変数置換やループで動的化する
  • values.yamlの分離: chart開発者と利用者の責任分界(chartは機能、valuesは設定)
  • subchartの静的依存: Helm chartはartifactとして配布されるので、依存はparse時に決定的でないと不便

得たもの

Kubernetes設定のwidely-adopted標準、エコシステム(Helm Hub, Artifact Hub)の充実、values.yamlによる設定/機能の分離。

失ったもの

静的型(template内の式は型なし、runtime errorが多い)、関数の自由度(高階関数なし、変数scopeの扱いが特殊)、デバッグ難(templateが展開されないと結果が見えない)。

章1 §1-3-4への当てはめ: Helmは「外部DSL × 言語が決める」象限の典型例。Terraform / Bicep / Carinaと並ぶが、typedじゃない点で特殊。

template engine系DSL (Go template, Jinja2等)は「文字列置換 + 限定的な制御フロー」を共通骨格とし、抽象化機構が薄い。Helmはその上にKubernetes用の便利関数(Sprig + lookup / tpl 等)を載せた形。

Crossplaneとの対比:両者ともYAMLベースだが、Helm = template engine、Crossplane = Composition pipelineで別アプローチ。Helmはconfiguration の生成、Crossplaneはconfiguration のreconciliation が主眼。

Carinaの立ち位置

ステータス:初稿(2026-04-27)。cross-DSL分析(11DSL)と章1 (CDK / Pulumi / Terraform / Carina比較)を踏まえたCarinaの立ち位置整理。

1.出発点:章1の4ツール比較での立ち位置

章1 §1-3-4でCarinaは「外部DSL × 言語が決める」象限に位置づけられた:

抽象化の追加言語が決める(fn / >> / |> / closure実装済み、高階関数未実装)
複数量の制御言語が決める(for 式 / if 式の専用構文のみ)
実装の切替言語が決める(source リテラル + use 式は let 束縛RHSのみ、二段で制限)

この象限の同居メンバはTerraform / Bicep / Helm / CUE / Crossplane (YAML層)。

2. cross-DSL分析で見えた発見

構成記述系11DSL (Pkl / Bicep / KCL / CUE / Dhall / Jsonnet / Nickel / cdktf / cdk8s / Crossplane / Helm)を3自由度で点検した結果、章1の4象限に第5象限が浮上した。

「外部DSL × ハイブリッド(抽象化追加だけ規約寄り)」象限

5DSL (Pkl / KCL / Dhall / Jsonnet / Nickel)が独立に同じパターンに収束:

抽象化の追加規約に委ねる (高階関数 / lambda / 継承などが自由)
複数量の制御言語が決める (専用comprehension or組込み再帰子)
実装の切替言語が決める (import pathリテラル)

これは「外部DSLを選びつつ、計算ロジックの再利用(関数)だけは汎用言語並みに開放、graph/value形状を変える2自由度だけ言語で縛る」という共通設計判断。実用上の必要性(環境別パラメタ計算 / 命名規則ヘルパー等を関数で再利用したい)からの自然な収束と読める。

graph出力DSLという別軸

11DSLを「何を出力するか」で分けると、章1の3自由度では捉えきれない別レイヤの差が浮上:

構成データ出力DSLPkl / KCL / CUE / Dhall / Jsonnet / Nickel
graph出力DSLTerraform / CDK / Pulumi / Carina / Bicep / cdktf / cdk8s / Crossplane / Helm

graph出力DSLのコードは(a)ノード + (b) edge を出す。state管理 / 差分計算 / CRUD実行はDSLのレイヤではなくツール(engine / CLI)のレイヤの話で、本分析(DSLの比較)では扱わない。

なお「コードからresource graphに至る経路」(直接出力 / ツリーsynth / RPCストリーム)の差は本分析の主題から外れる別軸。CDK / Pulumiもresource graph自体はedge込みで表現できるので「graph出力DSL」としてはTerraform / Carinaと同列。Terraform / Carinaとの差別化要因はgraph形状の静的予測可能性(章1 §1-3の3自由度議論) と評価副作用なし(章1 §1-3-6で他章送り、章2実行モデルで扱う) の組み合わせで説明できるので、ここでは独立軸として立てない。

3. Carinaが目指す位置取り:空席の象限

「graph出力DSL × ハイブリッド象限」の組み合わせを11DSLに当てはめると空席 (前掲のマトリクス参照)。

5DSLのハイブリッド象限への収束は構成データ出力DSLに限った観察であり、graph出力DSLでこの位置取りを実装した先例は存在しない。Carinaは高階関数を導入することでこの空席に踏み込める。

ただし5DSLに先行例がないため、graph出力DSLでハイブリッド象限を実装することは新しい設計象限の実証になる。

4.「IaC向きの言語」観点での評価

各DSLを「IaC (resource graphを出力する)に向くか」で評価すると、上位は:

  1. KCL (現実的解): 5DSLの中で唯一IaC領域の実例(Konfig / KusionStack)とエコシステムを持つ
  2. Pkl (理論的解):設計の整合性は高いが公開エコシステムが薄い
  3. Carina (高階関数追加後): graph出力を主目的とする点で5DSLと差別化できる、IaC専用に特化したハイブリッド象限DSLになる
  4. Crossplane (番外):「functionに任意言語を許す」設計でハイブリッド象限の問題を言語境界で逃がす第三の解

Carinaの独自性は「graph出力を最初から主目的とする」点。Pkl / KCLは構成データ出力が主目的で、IaCとして使うには別レイヤ(ツール側)の追加が要る。Carinaはgraph出力をDSLレベルで前提にしている。

5.高階関数を入れた場合のシミュレーション

Carinaに高階関数を導入すると、3自由度の対応が次のように変わる(章1 §1-3がgraph形状と属性値の両方を含む形に拡張されたことを踏まえた整理):

  • 抽象化の追加:言語が決める → 規約に委ねる (graph形状側 / 属性値側とも、関数値経由で抽象化を増やせる)
  • 複数量の制御:言語が決める(for 式)のまま(graph形状側 / 属性値側とも)
  • 実装の切替:言語が決める(source リテラル + use の位置制限)のまま(graph形状側)。属性値側は「計算ロジックの動的差し替え」が高階関数で可能になる

これはPkl / KCL / Dhall / Jsonnet / Nickelと同じハイブリッド象限への合流を意味する。5DSLの収束パターンと整合する自然な進化方向。ただし5DSLはgraph出力DSLではないので、構造的な類似(analogy)であって直接の先例(precedent)ではない。

境界設計:属性値計算の自由度をgraph形状に染み出させない

高階関数を導入する核心は属性値計算の自由度を上げることだが、これがgraph形状側(resource生成位置 / module選択位置 / identity決定位置)に染み出すと、章1 §1-3の「実装の切替」自由度を言語側で縛る不変条件が壊れる。AI時代の文脈(§7参照)ではplan予測精度・AI検証性の悪化として現れる。

例えば次のパターンを禁じる必要がある:

fn pick_module(env: string) -> Module { ... }
let net = (pick_module("prod")) { cidr = "..." }  # 関数呼び出し結果を module call の起点に

これを許すと、現状の不変条件(source リテラル限定 / use 式の位置制限)が骨抜きになる。「実装の切替」のgraph形状側だけを厳格分離するだけでは十分条件にならない:属性値レベルの関数値が、参照やbooleanを介して後段の for / if / module選択に流れれば結局graph形状を変えうる。境界設計の必要条件は「関数値がresource生成位置・module選択位置・identity決定位置に到達しない」という型/文法境界。

選択肢:

  1. 型レベル制約Module 型を関数の戻り値型 / 引数型に置けないようにする。さらにresource typeも関数値で扱えないようにする
  2. 文法レベル制約module call (name { ... })の起点に式を許さず、識別子のみ許す。同様にresource declarationの起点も識別子のみ
  3. 評価レベル制約関数値がmodule call / resource生成位置に評価された場合はparse/evaluatorで弾く

詳細は carina#2238 で議論。

抽象化境界の透明性との関係(仮説)

章1 §1-3-4で「予測可能性議論の射程を限定する前提」として記録された抽象化境界の透明性は、Carina固有のmodule機構と関わる仮説的観察がある: use 式とインスタンス化の分離(let network = use { source = ... }; let net = network { ... })、同一templateから複数インスタンス化、use 式の let RHS限定といった現状の設計は、moduleの境界を構文レベルで明示する性質を持つ。これは境界管理を明示しやすいという意味で、CDKの new SomeConstruct(scope, 'id', props) のような汎用言語の new 慣習よりも透明性に優位を持つ可能性がある。

ただし構文レベルでの明示性は、呼び出し側透明性そのものを自動では保証しない: module中身を読まずに呼び出し側だけでgraph形状 / 属性値を予測できるかは、依然としてmodule設計者のドキュメント文化・テスト文化・型情報の充実度に依存する。Carinaの構文設計は透明性を促す方向に効きうるが、それだけでAI検証性 / plan精度 / 静的監査が成立する保証にはならない。これは経験的検証が必要な仮説で、ここでは深追いしない。

6.「IaCで高階関数は本当に必要か」への懐疑

ハイブリッド象限への合流は構造的整合性の議論で、ユーザの実需要とは別の問題。実需要観点では:

高階関数なしで十分かもしれない根拠

  • Bicepが意図的に入れていない: Microsoft設計、func のみで高階関数は仕様にない。それでもAzure IaCとして広く使われている
  • Terraformが14年高階関数なしで運用: for_each / dynamic で大半の用途を満たしている
  • CDK / Pulumiの高階関数活用は実は限定的:命名関数や map でループ程度、Constructを関数で渡す/返すパターンは現場では稀

IaCで実際に必要な抽象化

  • 値計算の再利用:命名規則 / 環境別パラメタ → fn で十分
  • 構成のテンプレート化: VPC + Subnet × N + IGWのセット → moduleで十分
  • 多数生成: multi-region展開 / リスト要素ごと → for 式で十分

a, b, cでIaCの現実的な用途はカバーできる可能性が高い。高階関数は「あれば嬉しいが必須ではない」機能かもしれない。

取りうる立場

A.入れない(Bicep路線)「IaCでは値計算と構成テンプレート化で十分」と割り切る。Bicep成功の経験的裏付けあり
B.入れる(KCL路線)構造的に5DSLと整合、長期的拡張余地。ただし大改修コスト
C.保留現状の fn + 関数合成で実需要を観察、ユーザから具体ユースケースが出てきたら検討

Carinaの選択: 実験的プロジェクトという位置づけから、A / CよりB (積極導入)の方が学びが多い。境界設計(graph出力DSLでの高階関数)は5DSLに先行例がない領域なので、新しい設計象限の実証として価値が高い。「IaCで本当に必要か」の答えは入れてみないと分からない。

7.生成AI利用前提での予測可能性の意味

章1 §1-3が立てた予測可能性の基準は(本版で) 「実行前にコードを読んだ時点でresource graphの形と各ノードの属性値を読み取れるか」で、暗黙に読む主体は人間が前提だった。生成AIによるIaCコード生成・読解・修正が普及しつつある現在、この前提を再検討する必要がある。

予測可能性はgraph形状と属性値の両方に効く。実運用では「このリソースは具体的にどう設定されているか」をコードから知りたい場面(インシデント対応 / コンプライアンス監査 / セキュリティレビュー / IAMポリシー検査 / 暗号化設定確認)が頻出し、graph形状だけ見えても属性値が動的計算だらけだと運用上の予測可能性は半減する。

「人が直接読まない」前提だと予測可能性は何のため?

人が読まなくなったときに予測可能性が指す対象は次のどれか(graph形状側 / 属性値側の両方が論点になる):

観点内容AI時代での重要性
AIによるgraph + 属性値理解の精度 LLMが動的構造を持つコードからgraph形状と属性値を正しく推論できるか 高(AIも完璧ではなく、動的module選択 / 深い高階関数チェーン / 複雑な属性値計算で誤読する)
AI修正の安全性 「このリソースの暗号化を有効にして」「タグを追加して」とAIに頼んだとき、副作用範囲と既存属性値の整合性を正しく見積もれるか 高(属性値が動的計算で決まっているとAIも整合的な修正を出しにくい)
静的解析の効きやすさ lint / 型検査 / policy engine (例:「全S3 Bucketは暗号化必須」)が動的属性値で破綻しないか 変わらず重要(AIが読むかと独立)
plan/previewの正確性 ツール側のgraph抽出と差分計算が正しく動くか、属性値のunknownが増えすぎないか 高(静的予測可能性が低いとplanでunknown値だらけになり、人にもAIにも何が起きるか見えなくなる)
AIのコンテキスト窓 巨大IaCリポジトリでAIが全コードを一度に見られないとき、局所読みで判断できるか 高(コンテキスト制約は人と同質、局所読みでgraph形状と属性値が分かる性質が効く)
fail-safeガードレール AIが自律的にapplyする前提で、予期せぬ副作用を防げるか 高(「動的に何が起きるか分からない」をAIに丸投げできない)
コンプライアンス・セキュリティレビュー 「全IAM Roleの assume_role_policy を機械的に確認」「全RDSの storage_encrypted を検証」のような属性値レベルの監査ができるか 高(動的計算で属性値が決まると静的監査が破綻)

結論:予測可能性は依然重要、ただし根拠が組み替わる

章1 §1-3の予測可能性議論は人前提に縛られていない。静的解析・plan精度・AI解釈・コンプライアンス監査もすべて予測可能性の恩恵を受ける。むしろ生成AIの時代では:

静的に決定的なコード(graph形状も属性値も)はAIにも好都合 「人が読めればAIも読める」
AIも動的構造で誤読する、コンテキスト制約もある 「人が読めないがAIなら読める」は限定的
plan予測が崩れるとIaCの根本価値(apply前に結果を見せる)が毀損する 「人もAIも読めないがapplyはできる」は危険

つまり予測可能性の重要性の根拠が「人の認知負荷の軽減」から「機械可読性 + AI検証性 + plan精度 + AI自律applyのガードレール + 静的監査の成立性」に組み替わる。Carinaがgraph形状と属性値の両側で静的予測可能性を保つ設計を取ることの正当性は、AI時代にむしろ強まる。

高階関数導入議論への含意

§5の高階関数境界設計は、AI時代の文脈ではより重要度が上がる:

  • 高階関数を入れた境界設計が緩いとplanがunknownだらけ:人にもAIにも判別不能になる
  • AI自律applyの安全性:動的module選択や属性値の動的計算を許すとAIが事故を起こす範囲が広がる
  • 「AIが書くから人が読めなくていい」は破綻: AIが動的構造を多用したコードを生成すると、それを検証する人(またはレビューAI)のコストが跳ね上がる
  • 属性値レベルでも同じ問題: tags = compose(f, g, h)(env) のような複雑な合成は、graph形状を変えずとも属性監査を破綻させうる

§6の「IaCで高階関数は本当に必要か」議論についても、AI時代の観点から見直しの余地がある:

  • 値計算の再利用はAIが肩代わりできる:「環境別ポート計算ヘルパー」を関数で書く代わりにAIが一括展開した値を生成できる。高階関数の実需要はむしろ下がる可能性
  • 構成のテンプレート化もmoduleで十分: AIがmoduleを組み合わせる形で構成を生成できる
  • 多数生成も for 専用構文で十分: AIが for の専用構文を生成するのは難しくない

Bicepが高階関数を入れていない設計判断は、AI時代でむしろ正当化されやすい:表現力を絞ったDSLの方がAIにとっても扱いやすい(生成・読解・修正のすべてで)。Carinaの高階関数導入は構造的整合性(5DSLのハイブリッド象限合流)とAI時代の機械可読性(絞り込みを保つ)の間でトレードオフを取る設計判断になる。

実験的プロジェクトとしてのCarinaの位置づけは、このトレードオフを実証実験する余地を提供する。「高階関数を入れたDSLはAIにとっても扱いやすいか」「属性値計算の自由度を上げても静的監査は成立するか」は入れて使ってみないと分からない。

9.総合的な立ち位置

章1 + cross-DSL分析 + 機能点検をまとめると、Carina (DSL + ツール)は想定以上に成熟している:

  • 必須7項目 + import + moved + WASM providerまで揃っており、IaCツールとしての骨格は完成
  • 章1で示された「外部DSL × 言語が決める」象限の典型例としてTerraform / Bicepと並ぶ位置に既にいる

ここから先の進化方向は次の2軸。

軸1:運用補助機能の充実(実需要先行)

短期的に実用度を上げる方向。3つの未実装項目をカバー:

  • carina#2239 depends_on 相当
  • carina#2240 --target フラグ
  • carina#2241 carina drift コマンド

これらはgraph出力DSLの根本構造ではなく、実運用で使うための補助機能。Terraformに追従する漸進的改善。

軸2:新しい設計象限の実証(構造先行)

長期的に独自性を確立する方向。高階関数を導入してハイブリッド象限に踏み込む:

  • carina#2238 高階関数サポート
  • 境界設計で graph形状の静的予測可能性(章1 §1-3の「実装の切替」を言語が決める)を維持する:関数値が use / source 位置に染み出さないことが核心
  • 5DSLに先行例がない「graph出力 + 外部DSL × ハイブリッド象限」の実証

Carinaの独自性

  • graph出力 + 外部DSL + (将来的に)ハイブリッド:この3つの組み合わせを取るツールは現状存在しない
  • 実験的プロジェクトとしての位置づけが、軸2 (新象限の実証)を取る合理性を支える
  • 現状の機能点検結果から、軸1で実用性を保ちつつ軸2を実験できる状態にある

10.残された論点

  • 境界設計の技術的成立性:高階関数を入れたとき関数値がresource生成位置・module選択位置・identity決定位置に到達しない型/文法/評価制約が実装可能か(graph形状の静的予測可能性を保つ条件)
  • 属性値レベルの動的計算が静的監査に与える影響の経験的検証:高階関数経由で属性値計算が複雑化したとき、コンプライアンス監査 / セキュリティスキャン(例: tfsec, checkov相当)がどこまで成立するか
  • unknown値と高階関数の相互作用:関数引数/戻り値を流れるdeferred値の扱い
  • identityの安定性:高階関数経由で生成されるanonymous resourceの自動命名の安定性
  • plan表示:高階関数を経由した展開を予測可能な形で見せるUI設計(graph形状側 / 属性値側とも)
  • 「IaCで高階関数は実需要があるか」の経験的検証:入れた後でユーザがどう使うかの観察
  • 生成AIが動的構造を持つIaCコードでどの程度誤読・誤修正するか: AI時代の予測可能性議論を支える経験的根拠の収集(LLMベンチマーク、実運用事故の事例分析)。属性値レベルの動的計算とgraph形状レベルの動的計算でAI誤読率が異なるかも論点
  • 「人前提」と「AI自律apply前提」の予測可能性要件の差: §7では同方向と整理したが、AI自律でapplyまで完結する場合に追加で要件(より強い不変条件、例えばapply前のrollback可能性)が要るか
  • 11DSLの属性値計算自由度の再評価: cross-DSL分析の3自由度評価はgraph形状側に偏っている。Pkl / KCL / Dhall / Jsonnet / Nickelなど構成データ出力DSLは属性値計算が主用途なので、属性値自由度で見ると評価が変わる可能性がある。ここでは深追いしない(別issue)
  • 抽象化境界の透明性とCarinaの構文設計の関係: §5末尾で仮説として置いた「use + インスタンス化分離は境界管理を明示しやすいが、呼び出し側透明性そのものは保証しない」の経験的検証。実Carinaプロジェクトでのmodule設計プラクティス・ドキュメント文化・型情報充実度との相互作用を観察する必要がある
